The point in an agent's run where it stops and waits for a person.

Two shapes in one component, because they are the same moment: a single approve-or-reject decision, and a short run of questions the agent needs answering before it can carry on. Pass `questions` for the second.

The card stays in the transcript after it is answered, showing what was decided. What goes away is the machinery — the options, the fields and the buttons collapse once there is nothing left to do with them.

## Installation

ApprovalCard ships with the library — no separate install.

```tsx
import { ApprovalCard, FileIcon, Message, MessageScroller, Reasoning, Response, Surface, Task, Text } from 'panelui-native';
```

Or copy the source into your project, to own and edit it:

```bash
npx panelui-cli@latest add approval-card
```

## Usage

```tsx
<ApprovalCard
  title="Apply these changes?"
  description="Six files, one migration."
  status={status}
  onApprove={apply}
  onReject={discard}
/>
```

## Examples

### A decision

The plain case. Each button appears only if its handler was passed.

```tsx
const [status, setStatus] = useState<ApprovalCardStatus>('pending');

<ApprovalCard
  title="Apply these changes?"
  description="Six files, one migration. Nothing is written until you say so."
  status={status}
  onApprove={async () => {
    setStatus('submitting');
    await apply();
    setStatus('approved');
  }}
  onRequestChanges={() => setStatus('changes-requested')}
  onReject={() => setStatus('rejected')}
  result="Applied to main."
/>
```

### Showing what is being approved

`children` is the body — a diff, a summary, a preview. Anything that answers "approve what?" without the reader leaving the card.

```tsx
<ApprovalCard title="Send this reply?" status={status} onApprove={send} onReject={cancel}>
  <Surface className="gap-1 p-3">
    <Text className="text-xs text-muted-foreground">To: dana@example.com</Text>
    <Text className="text-sm">
      Thanks for the report — I have reproduced it and a fix is on the way.
    </Text>
  </Surface>
</ApprovalCard>
```

### A run of questions

Stepped rather than listed. A single choice moves on by itself; the last one waits for the submit button.

```tsx
const QUESTIONS: ApprovalCardQuestion[] = [
  {
    id: 'scope',
    title: 'How focused should the first release be?',
    options: [
      { value: 'focused', label: 'A focused starter set' },
      { value: 'broad', label: 'A broader collection' },
    ],
    allowCustom: true,
    customPlaceholder: 'Describe another scope…',
  },
  {
    id: 'platforms',
    title: 'Which platforms should it ship on?',
    multiple: true,
    options: [
      { value: 'ios', label: 'iOS' },
      { value: 'android', label: 'Android' },
      { value: 'web', label: 'Web' },
    ],
  },
];

<ApprovalCard
  questions={QUESTIONS}
  status={status}
  submitLabel="Send answers"
  onSubmit={(answers) => reply(answers)}
  result="Two responses sent to the agent."
/>
```

### Waiting on the server

`submitting` holds the card open and disables everything in it, which is the state to show while the call is in flight.

```tsx
<ApprovalCard
  title="Deploy to production?"
  status={deploying ? 'submitting' : status}
  onApprove={deploy}
  onReject={cancel}
/>
```

### Answered, and left in place

The card stays in the transcript with its verdict. An approval that disappears leaves a conversation in which something clearly happened and nothing says what.

```tsx
<ApprovalCard
  title="Apply these changes?"
  status="approved"
  result="Applied to main, 4 minutes ago."
/>
```

## Versions

### In a run

The card in the place it belongs: a transcript that stops at it. The agent reports what it has done, asks, and only carries on once the answer is in — which is the whole reason the component exists, and the thing a card on its own cannot show.

```tsx
const [status, setStatus] = useState<ApprovalCardStatus>('pending');
const answered = status !== 'pending' && status !== 'submitting';

<MessageScroller className="flex-1">
  <MessageScroller.Viewport>
    <MessageScroller.Content className="gap-4 px-5 py-6">
      <MessageScroller.Item messageId="ask">
        <Message align="end">
          <Message.Content>
            <Message.Bubble>
              <Message.BubbleContent>
                Tidy up the release branch and cut 0.9.0.
              </Message.BubbleContent>
            </Message.Bubble>
          </Message.Content>
        </Message>
      </MessageScroller.Item>

      <MessageScroller.Item messageId="work">
        <View className="gap-2">
          <Task status="complete">
            <Task.Trigger title="Read the branch" />
            <Task.Content>
              <Task.Item>
                Opened <Task.File icon={<FileIcon size={12} />}>CHANGELOG.md</Task.File>
              </Task.Item>
              <Task.Item>Found 3 commits to squash</Task.Item>
            </Task.Content>
          </Task>

          <Reasoning defaultOpen={false} duration={4}>
            <Reasoning.Trigger />
            <Reasoning.Content>
              Two of the three are documentation-only, so squashing them loses
              nothing. The third is a contributor&apos;s, and squashing it drops
              their authorship — which is not mine to decide.
            </Reasoning.Content>
          </Reasoning>
        </View>
      </MessageScroller.Item>

      <MessageScroller.Item messageId="approval">
        <ApprovalCard
          title="Squash all three commits?"
          description="One is a contributor's, and squashing drops their authorship."
          status={status}
          onApprove={() => setStatus('approved')}
          onRequestChanges={() => setStatus('changes-requested')}
          onReject={() => setStatus('rejected')}
          result={
            status === 'approved'
              ? 'Squashed all three.'
              : status === 'changes-requested'
                ? 'Squashed the two documentation commits, kept the third.'
                : 'Left the history alone.'
          }
        />
      </MessageScroller.Item>

      {answered ? (
        <MessageScroller.Item messageId="done">
          <Response>
            {status === 'rejected'
              ? 'Left the history as it was. 0.9.0 is tagged from the branch unchanged.'
              : '0.9.0 is tagged and the branch is clean.'}
          </Response>
        </MessageScroller.Item>
      ) : null}
    </MessageScroller.Content>
  </MessageScroller.Viewport>
</MessageScroller>
```

## Variants

### `status`

- `pending` *(default)*
- `submitting`
- `approved`
- `answered`
- `rejected`
- `changes-requested`


## Notes

### Which shape you get

Without `questions` it is an approval: a title, whatever you put in `children`, and a row of buttons. Each button appears only if you passed its handler, so a card with `onApprove` alone is a single-button acknowledgement rather than a decision with a missing half.

With `questions` it is a stepped run of them, and the approval buttons are replaced by Back, a row of dots, and Next — or your `submitLabel` on the last one.

### One question at a time

Listed out, a run of questions is a form. Stepped, it is a conversation, which is what the transcript around it already is.

A single-choice question advances itself shortly after it is answered. Long enough for the disc to fill and be seen filling, short enough that it reads as the card responding. Set `autoAdvance: false` on a question where the reader should confirm each answer, and note that multiple-choice questions never advance themselves — the reader is still adding to the answer — nor does the last one, where moving on means submitting.

`allowCustom` adds a field for an answer that is not on the list. On a single-choice question the two are alternatives, so choosing from the list clears the field; on a multiple-choice one they sit alongside each other.

### Status, and who owns it

`status` is yours to move. The card does not set it: approving fires `onApprove` and waits, because the action usually has to reach a server before it is true.

`submitting` keeps the card open and disables everything in it, which is what to show while that call is in flight. `approved`, `rejected`, `changes-requested` and `answered` all close it and print `result` — or the status's own words, if you pass nothing.

### It is built out of the library

RadioGroup, Checkbox, Input and Button, not redrawn versions of them. An approval that styles its own radio is one that stops matching the app's radios the first time either changes — so a theme change reaches this card the same way it reaches everything else.

### Announcing it

The result is a live region, so a screen reader is told the outcome when the card closes rather than having to go looking. The row of dots is labelled once, as a row: a dot cannot be read, and eight of them announced one at a time is noise standing in for the counter that is already in the header.
