Segmented navigation with one indicator that springs between measured trigger positions. A single thing travelling is what makes a switch two tabs away read as one movement rather than as two states swapping.

## Installation

Tabs ships with the library — no separate install.

```tsx
import { Tabs, Text, Button, Input, Badge, PackageIcon, MessageCircleIcon, CalendarIcon } from 'panelui-native';
```

Or copy the source into your project, to own and edit it:

```bash
npx panelui-cli@latest add tabs
```

## Usage

```tsx
<Tabs defaultValue="account">
  <Tabs.List>
    <Tabs.Trigger value="account">Account</Tabs.Trigger>
    <Tabs.Trigger value="password">Password</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="account">…</Tabs.Content>
  <Tabs.Content value="password">…</Tabs.Content>
</Tabs>
```

## Composition

```tsx
<Tabs>
  <Tabs.List>
    <Tabs.Trigger value="…">…</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="…">…</Tabs.Content>
</Tabs>
```

- **`Tabs.List`** — Holds the triggers and the animated indicator. Takes `scrollable` for more tabs than fit.
- **`Tabs.Trigger`** — One tab, with optional `icon`, `badge` and `disabled`. Must be inside `Tabs.List`.
- **`Tabs.Content`** — Panel for a tab. Unmounted while inactive unless the root sets `keepMounted`.

## Examples

### Uncontrolled

`defaultValue` is required — the tabs need a starting panel.

```tsx
<Tabs defaultValue="overview">
  <Tabs.List>
    <Tabs.Trigger value="overview">Overview</Tabs.Trigger>
    <Tabs.Trigger value="activity">Activity</Tabs.Trigger>
    <Tabs.Trigger value="settings">Settings</Tabs.Trigger>
  </Tabs.List>

  <Tabs.Content value="overview">
    <Text>Usage and billing at a glance.</Text>
  </Tabs.Content>
  <Tabs.Content value="activity">
    <Text>Everything that happened this week.</Text>
  </Tabs.Content>
  <Tabs.Content value="settings">
    <Text>Names, members and integrations.</Text>
  </Tabs.Content>
</Tabs>
```

### Controlled

Needed when something outside the tab strip changes the panel — a deep link, or a button in one panel that jumps to another.

```tsx
const [tab, setTab] = useState('overview');

<>
  <Button onPress={() => setTab('settings')}>Go to settings</Button>

  <Tabs value={tab} onValueChange={setTab} defaultValue="overview">
    {/* …list and content… */}
  </Tabs>
</>
```

### More tabs than fit

A fixed row splits its width between the triggers, which crushes every label once there are more than about four. `scrollable` gives each trigger its natural width, puts the row in a horizontal scroller, and scrolls the active tab into view when it changes from elsewhere.

```tsx
<Tabs variant="underline" defaultValue="overview">
  <Tabs.List scrollable>
    {sections.map((s) => (
      <Tabs.Trigger key={s.id} value={s.id}>{s.name}</Tabs.Trigger>
    ))}
  </Tabs.List>

  {/* …content… */}
</Tabs>
```

### Icons, badges and disabled tabs

A count or a status goes in `badge` rather than into the children, so the label keeps its own typography. A disabled trigger is dimmed, unselectable, and announced as disabled.

```tsx
<Tabs.List>
  <Tabs.Trigger value="inbox" icon={<InboxIcon size={16} />}>
    Inbox
  </Tabs.Trigger>
  <Tabs.Trigger value="activity" badge={<Badge variant="secondary">4</Badge>}>
    Activity
  </Tabs.Trigger>
  <Tabs.Trigger value="archived" disabled>
    Archived
  </Tabs.Trigger>
</Tabs.List>
```

### Keeping panels mounted

By default a panel is unmounted when you leave it, and a scroll position or a half-filled form goes with it. `keepMounted` renders every panel and hides the inactive ones — not drawn, not touchable, out of the screen-reader order, but still there. It costs the render of every panel up front, so it is opt-in. Pass `"measured"` instead of `true` when a hidden panel needs to keep its **size** as well, which is what a virtualised list inside one needs in order to render any rows at all.

```tsx
<Tabs keepMounted defaultValue="draft">
  <Tabs.List>
    <Tabs.Trigger value="draft">Draft</Tabs.Trigger>
    <Tabs.Trigger value="preview">Preview</Tabs.Trigger>
  </Tabs.List>

  <Tabs.Content value="draft">
    <Input label="Title" value={title} onChangeText={setTitle} />
  </Tabs.Content>
  <Tabs.Content value="preview">…</Tabs.Content>
</Tabs>
```

### Swiping between panels

With `swipeable`, dragging sideways on the panel moves to the next or previous tab. The gesture only takes over after 12pt of sideways travel and gives up on any real vertical travel, so a panel that scrolls still scrolls. It is off by default: a panel may already contain something that wants a horizontal drag, and the two cannot both have it.

```tsx
<Tabs swipeable defaultValue="mon">
  <Tabs.List scrollable>
    {days.map((day) => (
      <Tabs.Trigger key={day.value} value={day.value}>
        {day.label}
      </Tabs.Trigger>
    ))}
  </Tabs.List>
  {days.map((day) => (
    <Tabs.Content key={day.value} value={day.value}>
      <Card>…</Card>
    </Tabs.Content>
  ))}
</Tabs>
```

## Notes

### Swiping

A swipe changes tab on release, not while the finger is down — it commits once the drag has passed a quarter of the panel's width, or once it is moving faster than 500pt/s however short it was.

The panel tracks the finger one to one. Only one panel is mounted at a time unless `keepMounted` is set, so there is nothing behind the one being dragged; instead of holding it back, the panel dims as it travels and the arriving one comes back up through the same fade. The movement carries the change, and the dissolve covers the gap.

On release the arriving panel picks up a whole panel's width from wherever the outgoing one was let go — which is where it would have been all along had both been mounted — and springs to rest carrying the speed the finger let go at. That is what makes a swipe one continuous movement rather than a drag followed by a separate slide. A tab changed by pressing a trigger has no travel to continue from, so it is given a shorter throw of its own, in the direction the tab sits.

The order swiped through is the order the triggers are **written** in, not the order they appear on screen. Under RTL those differ — the first tab is the rightmost — and a swipe towards the start of the reading direction goes to the previous tab in both.

At the first and last tab the panel still moves, but a sixth as far. A gesture that produces nothing at all is indistinguishable from one that was not received.

### The expanding variant

A row of icon pills where only the selected one is open: it widens to let its label out and closes again behind it. For a short row of destinations that are recognisable by their icons, where writing every label out takes the whole width to say four words nobody rereads after the first time.

Give **every** trigger an `icon`. A closed tab has nothing else, and one without an icon closes to an empty pill.

There is no travelling indicator here, because every tab draws its own pill and a shape sliding underneath them would be invisible. The shape that moves is the open tab itself. The open pill sits one step further from the page than the closed ones — lighter in a dark theme, darker in a light one — which is what the tertiary surface token means, and why the selection is a surface rather than a colour.

The label is never unmounted, only closed over: a row of unlabelled icons has nothing for a screen reader to read out, and a label that mounted on selection would have no width to animate *from*, so the pill would jump to its open size and the text fade in inside it. Under the system's reduce-motion setting it opens and closes with no animation at all.

The opening is a curve rather than a spring, because it animates a width: every frame of it is a layout pass and the whole row moves with it, so a spring's overshoot slides the last word in, out and back in again and takes the row with it. The label's opacity trails the width rather than leading it — text drawn into a box narrower than itself is text with its end cut off.

The width it opens to is measured from a second copy of the label, laid out once in a box wide enough not to constrain it and never drawn. The label cannot be measured where it sits, because the box it sits in is the box being resized.

### What a swipe costs, and what it does not

`swipeable` does not change what is mounted. Only `keepMounted` decides that, so a swipe animates between two panels of which one is being unmounted and the other mounted for the first time — exactly what a press does, and exactly as many panels as a press mounts.

What it changes is *when* the mount happens: during a movement rather than before a still frame. A panel that is expensive to build — a long list, a chart, anything that measures itself — turns from a pause before it appears into a stutter in the slide. If swiping feels heavier than pressing on the same tab set, that is the panel's mount cost becoming visible, and the fix is whichever `keepMounted` actually keeps that panel's content built — see below. Turning `swipeable` off only hides it.

The drag itself moves the panel with a transform and nothing else, which costs the same whatever is inside it. On iOS the panel also fades as it travels; on Android it does not, because a view group there has no layer to fade and the alpha would be pushed down into every row on screen, re-drawing all of them on every frame of the gesture.

### What `keepMounted` keeps

`keepMounted` has three settings, and they differ in how much of a hidden panel is left standing.

`false`, the default, unmounts an inactive panel. Its state goes with it: a scroll position, a half-filled form, a loaded page of results are all gone by the time you come back.

`true` keeps the panel mounted and hides it with `display: none`. State survives, and it is cheap — but `display: none` also takes the panel **out of layout**, so it is mounted at zero size.

That last part matters more than it sounds. A child that decides what to render by measuring the space it was given — a virtualised list asking its parent how tall it is, then filling that many rows — measures zero inside a hidden panel, and renders no rows. Its first real render still happens on the frame the tab becomes visible, which is the stall `keepMounted` looks like it should have removed. With the flag on or off, the tab change costs the same.

`'measured'` is the setting for that case. A kept panel stays laid out at the full size of the tab set and is hidden by not being drawn, rather than by being removed from layout. A list inside it measures properly, renders its rows and settles while it is still hidden, so becoming visible costs nothing.

```tsx
<Tabs defaultValue="users" keepMounted="measured" swipeable>
  <Tabs.List>
    <Tabs.Trigger value="users">Users</Tabs.Trigger>
    <Tabs.Trigger value="domains">Domains</Tabs.Trigger>
  </Tabs.List>

  <Tabs.Content value="users">
    <FlashList data={users} renderItem={renderUser} />
  </Tabs.Content>
  <Tabs.Content value="domains">
    <FlashList data={domains} renderItem={renderDomain} />
  </Tabs.Content>
</Tabs>
```

The trade is real, and is why it is not the default: every kept panel lays out and draws, up front and again on every size change, so a five-tab set builds five panels' worth of rows in order to show one. It buys a smooth tab change with a slower first render of the screen.

So: leave it at `false` unless panel state needs to survive, `true` when it does, and `'measured'` when a panel is slow to appear *and* its content sizes itself from the space it is given. A hidden panel is never drawn, never touchable and never in the accessibility tree under any of the three.
